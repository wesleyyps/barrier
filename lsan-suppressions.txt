# LeakSanitizer suppression file for barrier
# Usage: LSAN_OPTIONS=suppressions=lsan-suppressions.txt ./unittests
#
# HOW TO ADD A SUPPRESSION:
#   Use "leak:<symbol>" where <symbol> is a substring of a stack frame in the
#   leak trace. The rule fires if ANY frame in the allocation stack matches.
#
# Guidelines:
#   - Only suppress leaks that are INTENTIONAL by design (singletons, statics)
#     or are in test-only infrastructure that mirrors production behavior.
#   - Document WHY each suppression is necessary.

# ---------------------------------------------------------------------------
# ArchMultithreadPosix singleton (64 bytes)
# Allocated once in Arch::Arch() which is called from main(). The Arch object
# is a program-lifetime singleton and is never explicitly destroyed. This is
# intentional -- the destructor cannot be safely called at exit because other
# global objects depend on it.
# ---------------------------------------------------------------------------
leak:ArchMultithreadPosix::ArchMultithreadPosix

# ---------------------------------------------------------------------------
# IKeyState::KeyInfo::alloc -- unit test infrastructure leak
# KeyState::sendKeyEvent() allocates KeyInfo via malloc() and passes it to
# IEventQueue::addEvent(). In production the real EventQueue frees it via
# Event::deleteData() after dispatch. In unit tests MockEventQueue::addEvent()
# is a gMock stub that does nothing, so the KeyInfo is never freed.
# This is a test-infrastructure limitation, not a production code bug.
# ---------------------------------------------------------------------------
leak:IKeyState::KeyInfo::alloc

# ---------------------------------------------------------------------------
# SocketMultiplexer thread handle (64 bytes × N tests)
# SocketMultiplexer spawns a background multiplexer thread inside its
# constructor. Integration tests create SocketMultiplexer objects on the
# stack. When tests complete the thread handle allocated in
# ArchMultithreadPosix::newThread() is not freed because the multiplexer
# thread may still hold a self-reference through the thread system.
# This is a pre-existing issue in the test infrastructure, unrelated to the
# production code paths fixed in this session.
# ---------------------------------------------------------------------------
leak:ArchMultithreadPosix::newThread

# ---------------------------------------------------------------------------
# XWindowsScreen test object (288 bytes)
# XWindowsScreenTests creates an XWindowsScreen but does not fully destroy
# it. The screen object owns X11 resources that it allocates in its
# constructor. Pre-existing issue, not affected by our changes.
# ---------------------------------------------------------------------------
leak:XWindowsScreen::XWindowsScreen
